# Live test: Govee H6076 floor lamp, 2026-10-29

The main agent ran this test first, on the user's request (`t14`, deviation
`d23`). The user's own run follows it. Only measured numbers are recorded
here. The lamp's IP address and device id are private and left out.

## Setup

- **Lamp:** Govee H6076 floor lamp. The scan reports `sku` H6076, Wi-Fi
  firmware 1.00.16 and BLE firmware 1.04.05. LAN Control was turned on in
  Govee Home.
- **Host:** spark, on the home Wi-Fi interface `wlP9s9`. There was no
  `GOVEE_API_KEY`, so this test is LAN only.
- **Software:** govee-cli 0.11.0 from branch `lamp/integration`, installed
  with `uv tool install`.
- **Starting state:** on, brightness 7, white at 5208 K. The test restored
  this state at the end.

## Discovery

| Check | Result |
|-------|--------|
| Multicast scan to 239.255.255.250:4001 | **No reply** in 6 tries. SSDP on the same group got replies from other hosts, so spark's receive path works. |
| Unicast scan to the lamp's address on port 4001 | Reply. It has no `ip` field, so the address comes from the sender. |
| Status query (`devStatus`) to port 4003 | Reply on 4002 with `onOff`, `brightness` and `colorTemInKelvin`. Sending it to 4002 gets nothing. Plan risk `r1` is resolved. |
| Discovery fallback, empty cache | multicast, then sweep: found by **sweep** in 6.0 s. |
| Discovery fallback, cached | cache plus multicast: found by **cache** in 3.0 s, then **0.64 s** after the early-return fix. |

## Over the LAN address

`govee serve` was bound to `0.0.0.0`, and the client reached it through
spark's own LAN address. Serve therefore saw a non-loopback client, as it
would see a phone. That client was spark itself, not a phone.

| Check | Result |
|-------|--------|
| Pairing link | Printed with the LAN host, ready to open on a phone. |
| `/api/health` without a token | 200 |
| `/api/state` without a token | 401 |
| A write with no `Origin`, or with a loopback `Origin` | 403 |
| A write with the matching LAN `Origin` | 200, status confirmed |
| Spoofed `X-Govee-Source: mcp` / `X-Govee-Actor` from the LAN client | Ignored; logged as `web` and the token's name |
| SIGTERM to serve | Clean stop: the log shows `govee serve stopped` |

## Findings fixed during the run

1. **Lamp at 1 % after a fade-out.** A fade-out leaves the lamp off at
   brightness 1, and a brightness command wakes an off lamp, so the level
   cannot be restored while the lamp is off. Govee's turn-on now restores the
   remembered level (`5460508`, deviation `d22`). Turning the lamp on from the
   Govee app or its button after a fade-out still lights it at 1 %.
2. **SIGTERM skipped the clean shutdown.** Serve died in the default handler,
   so the poller was not stopped and running fades were not cancelled. It now
   takes the Ctrl-C path (`2a6e764`).
3. **Discovery waited the whole scan window** even when the cached lamp had
   already answered. It now returns 0.3 s after every expected address
   replies (`1657e45`).
